# Security

What this deployment does about security, and what it does not.

## Posture at a glance

| Area | Here | Gap |
|---|---|---|
| Secrets | Generated at deploy time, never in git | Kubernetes Secrets are base64, not encrypted |
| Database credentials | Generated by CloudNativePG, never leave the cluster | none |
| Redis | Password required, not optional | No TLS between n8n and Redis |
| Network | Default-deny, seven explicit allows, enforced | none |
| Transport | Plain HTTP | No TLS at the edge |
| Identity | One owner account | No SSO, no per-team isolation |
| Images | Pinned to exact tags | Not pinned by digest |

## Secrets

Nothing secret is committed. Three sources, and each credential is generated by whatever owns it:

| Secret | Generated by | Holds |
|---|---|---|
| `n8n-pg-app` | CloudNativePG, when it creates the database | PostgreSQL username and password |
| `n8n-redis` | `scripts/30-secrets.sh`, `openssl rand -base64 24` | Redis password |
| `n8n-app` | `scripts/30-secrets.sh`, same | n8n encryption key, editor login |

`scripts/30-secrets.sh` is idempotent: if a Secret exists it is left alone. Re-running it never
rotates anything, which is deliberate. See below.

`gitleaks` runs on every commit via `.pre-commit-config.yaml`, because "we generate secrets at
deploy time" is a convention, and conventions need a check.

### The encryption key

`N8N_ENCRYPTION_KEY` is the key n8n encrypts stored credentials with, and it deserves its own
paragraph because it behaves unlike any other value here.

- **Main and every Worker must have the same one.** A Worker with a different key cannot decrypt
  the credentials on a workflow it was handed; the execution fails at the node that uses them,
  with an error that does not mention encryption.
- **Rotating it destroys data.** Every credential already in the database becomes permanently
  undecryptable. There is no re-encrypt path.
- **A database backup is useless without it.** Restore the database with a different key and you
  get every workflow and not one working credential. It has to be backed up separately, and
  stored somewhere the database backup is not.

### What Kubernetes Secrets are not

They are base64, not encryption. Anyone with `get secret` in the namespace can read every value,
and so can anyone with read access to etcd. That is acceptable for a local cluster and not for a
real one; the production answer is External Secrets Operator or Vault, with etcd encryption at
rest enabled. See [production.md](production.md).

## Network isolation

[`kubernetes/80-networkpolicy.yaml`](../kubernetes/80-networkpolicy.yaml) denies all ingress and
egress in the `n8n` namespace and then allows six flows: DNS, Gateway to Main, n8n to PostgreSQL
and Redis, replication between the data pods, the operators reaching what they manage, and Workers
to the internet.

Two things about that last one:

- **Only Workers get internet egress.** Workflows call external APIs, so Workers need it. Main
  does not (it talks to the database and the queue), and a Main that can reach the internet is
  useful mainly to an attacker who has found a way to make it do so.
- **The rule excludes private address space.** `0.0.0.0/0` without `except` for the RFC 1918
  ranges would also grant a Worker access to every pod and Service in the cluster, which is the
  opposite of what "may call an external API" is meant to allow.

These are enforced, not decorative: kind's default CNI has supported NetworkPolicy since v0.24,
and `make drill` verifies it by making a connection that must be refused. On a cluster whose CNI
ignores NetworkPolicy, these objects are accepted and silently do nothing. Check this before
relying on them.

## The gaps, and what closes them

**Plain HTTP.** Traffic to the Gateway is unencrypted, including the editor login. That is also
why `N8N_SECURE_COOKIE=false` is set: n8n marks its auth cookie `Secure` by default, browsers
refuse to store a `Secure` cookie over HTTP, and the login silently fails. The setting is correct
*only* because there is no TLS. Adding TLS means adding cert-manager, a certificate on the Gateway
listener, and removing that flag. All three, together.

**One shared account.** No SSO, no projects, no per-team credential isolation. n8n's SSO and
project features are Enterprise-licensed; the community fallback is an authenticating proxy in
front of n8n, which is weaker because n8n then has no per-user identity of its own.

**Workflow code is arbitrary code.** Anyone who can edit a workflow can write an HTTP Request node
that reaches anything the Worker's network position allows. That is what the egress policy is
for, and it is the reason to think about separate Worker pools per sensitivity tier before
handing the platform to several teams.

**Images are pinned by tag, not digest.** A tag can be repointed upstream. Digests would be
stricter and are what a production deployment should use; tags are kept here because a reader
looking at `n8n:2.37.10` learns something that `n8n@sha256:4b76b9...` does not tell them.
